Execute mock trades and watchlist changes even in mock mode — the mock response includes {"ticker": "AAPL", "side": "buy", "quantity": 1} and {"ticker": "PYPL", "action": "add"} so all code paths are exercised. Treat the mock response the same as a real LLM response: parse it into LLMResponse, then proceed to execution + persistence. Do NOT return early before execution — only skip the actual litellm call.

    3. D-03 conversation history: SELECT role, content FROM chat_messages WHERE user_id='default' ORDER BY created_at ASC LIMIT 20. Build messages list: [{"role": "system", "content": system_prompt}] + history messages + [{"role": "user", "content": req.message}].

Collect result strings in actions_log (success: "Executed buy 1 AAPL @ $150.00", failure: the reason). Do NOT raise HTTPException — only append to actions_log.

    7. D-05 snapshot: if any trades were in result.trades (regardless of success/failure), call record_portfolio_snapshot(get_db_path(), state.price_cache) once.

    8. D-06 watchlist changes: iterate result.watchlist_changes. For action="add": check duplicate in DB, if not duplicate call await state.market_source.add_ticker(ticker), INSERT watchlist row.     9. D-04 append actions_log to message: if actions_log is non-empty, append "\n\n" + "\n".join(actions_log) to result.message.

    10. D-13 assistant message persistence: INSERT into chat_messages with role='assistant', content=result.message, actions=json.dumps({"trades": [t.model_dump() for t in result.trades], "watchlist_changes": [w.model_dump() for w in result.watchlist_changes]}).

    11. Return dict with keys: message (result.message), trades ([t.model_dump() for t in result.trades]), watchlist_changes ([w.model_dump() for w in result.watchlist_changes]).

    The fallback path (D-01): if LLM call fails, result has trades=[] and watchlist_changes=[], so execution loops are no-ops. User message was already persisted before the try block. Fallback assistant message is persisted after. Return shape is identical.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client -> POST /api/chat | User-supplied message field is unvalidated natural language |
| LLM response -> trade execution | Structured JSON from OpenRouter is treated as executable instructions |
| LLM response -> watchlist | Ticker symbols from LLM are inserted into DB without external validation |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-01 | Tampering | trade execution in chat.py | mitigate | Same cash/shares validation as manual trades applied to every LLM-triggered trade; validation runs inside BEGIN IMMEDIATE transaction |
| T-03-02 | Elevation of Privilege | LLM response -> arbitrary trade sizes | mitigate | Quantity validated positive (Pydantic float); cash/shares check rejects over-budget trades; max loss bounded by account balance |
| T-03-03 | Spoofing | LLM_MOCK env var | accept | Mock mode is a developer/test facility; no auth boundary in single-user app; risk is zero in production if env var is not set |
| T-03-04 | Information Disclosure | system prompt contains full portfolio | accept | Single-user app with no auth; portfolio context sent to OpenRouter is the intended design; no PII beyond virtual positions |
| T-03-05 | Denial of Service | LLM call timeout blocking handler | mitigate | All LLM exceptions caught by try/except (D-01); handler always returns 200 with fallback; no unbounded retries |
| T-03-06 | Injection | ticker symbol from LLM inserted into DB | mitigate | All DB writes use parameterized queries (sqlite3 ? placeholders); ticker uppercased and stripped; no string interpolation in SQL |
</threat_model>
